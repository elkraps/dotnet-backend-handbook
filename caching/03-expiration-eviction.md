## Политики

Когда кеш заполняется, нужно удалять старые или наименее нужные записи.

### TTL (Time-To-Live)

Запись удаляется через фиксированное время после записи.

```csharp
// Absolute TTL: становится недействительной через 5 минут
new DistributedCacheEntryOptions
{
    AbsoluteExpirationRelativeToNow = TimeSpan.FromMinutes(5)
}
```

**Absolute TTL** — удаляется через X времени с момента **записи**.
**Sliding TTL** — удаляется через X времени с момента **последнего доступа**. Активно используемые записи живут дольше.

```csharp
// Sliding: сбрасывается при каждом доступе
new DistributedCacheEntryOptions
{
    SlidingExpiration = TimeSpan.FromMinutes(10),
    // Максимальный срок жизни даже при активном использовании
    AbsoluteExpirationRelativeToNow = TimeSpan.FromHours(1)
}
```

**Проблема Sliding TTL:** популярные данные никогда не обновляются → stale data. Поэтому всегда комбинируй с AbsoluteExpiration.

### LRU (Least Recently Used)

При заполнении кеша вытесняется запись, к которой **дольше всего не обращались**.

```
Доступы: A B C D A B  (кеш на 3 элемента)
State: [A B C] (от старого доступа к новому)
D пришёл → вытесняем A
State: [B C D]
A пришёл → вытесняем B → State: [C D A]
B пришёл → вытесняем C → State: [D A B]
```

LRU оптимален для **temporal locality** — если обращался недавно, вероятно обратишься снова.

Redis использует **approximate LRU** (не точный): при вытеснении берёт случайные N ключей и удаляет самый старый из них (экономит память на точной LRU-структуре).

### LFU (Least Frequently Used)

Вытесняется запись, к которой обращались **реже всего**.

Лучше LRU для **frequency locality** (популярные данные — навсегда в кеше), но плохо работает при изменении паттернов доступа (вчера популярный ключ сегодня уже не нужен).

Redis 4.0+ поддерживает LFU через `maxmemory-policy allkeys-lfu`.

### Другие политики

| Политика | Вытесняет | Применение |
|---------|-----------|-----------|
| **FIFO** | Самый старый по времени записи | Простые очереди |
| **Random** | Случайную запись | Когда доступ равномерен |
| **allkeys-lru** | LRU среди всех ключей | Общий кеш |
| **volatile-lru** | LRU только среди ключей с TTL | Смешанный (сессии + постоянное) |
| **allkeys-lfu** | LFU среди всех ключей | Популярные данные |
| **volatile-ttl** | Ключ с ближайшим TTL | Когда важнее TTL |
| **noeviction** | Никого, возвращает ошибку | Когда потеря недопустима |

```bash
# Redis конфигурация
maxmemory 2gb
maxmemory-policy allkeys-lru
```

Expiration и eviction — разные механизмы: TTL ограничивает действительность записи, вытеснение освобождает память. Физическое освобождение не обязано происходить точно в момент TTL. В Redis политика задаётся конфигурацией; LRU не является универсальным значением по умолчанию.

## Подводные камни

Sliding TTL без absolute limit позволяет популярной записи жить бесконечно. noeviction означает ошибки записи при нехватке памяти, а не защиту от потери при сбое.
